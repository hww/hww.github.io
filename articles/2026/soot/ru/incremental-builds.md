# Инкрементальная сборка в sootc

## 1. Проблема

Пересборка проекта целиком дорога. Чем больше модулей, тем больше времени тратится на то, что не изменилось. Внешние системы сборки (Make, CMake, Ninja) умеют не пересобирать то, что не изменилось, но они знают только **mtime файлов** и **явно объявленные зависимости**. Они не знают, что sootc делает внутри.

Для C/C++ это работает: `gcc` компилирует один `.c` в один `.o`, зависимости выражаются через `#include` и `.d`-файлы. Для sootc так не работает. И это не мелкая деталь, а следствие устройства компилятора.

## 2. Почему инкремент должен быть внутри компилятора

Когда sootc компилирует `foo.sc`, он не просто читает один файл. Он:

1. Загружает prelude (`lib.st` + `lib.sc`) в интерпретатор.
2. Загружает `bar.sc` (и его зависимости) в память.
3. Строит дерево узлов для `foo.sc` **в контексте** уже загруженных зависимостей.
4. Только после этого генерирует `.bin`.

Если CMake запустит `sootc` отдельно на каждый файл, каждый процесс **заново** загрузит bootstrap и заново разберёт все зависимости. Для проекта из десяти модулей это десять загрузок bootstrap и десять разборов одного и того же `bar.sc`. Выигрыш от «не пересобирать неизменившееся» съедается стоимостью повторной загрузки.

Отсюда идея: сделать **сам компилятор** достаточно умным, чтобы решать, что пересобирать, и делать это **в одном процессе**, где bootstrap и зависимости уже загружены. Внешняя система сборки остаётся, но она запускает `sootc` **один раз** на проект, а не по разу на файл.

Именно поэтому в sootc появились:

- `--force` и `--incremental` — режимы сборки;
- `build-mode` в конфиге, `SOOT_BUILD_MODE` в env, `(opt "build-mode")` в REPL;
- отдельные `out-dir` и `header-dir` — чтобы артефакты не смешивались с исходниками;
- `BuildInfo` в `.bin` — чтобы решение «грязный/свежий» принималось по содержимому, а не по mtime.

## 3. Идея: `.bin` как манифест

В `.bin` уже есть entry `requires` — список имён модулей, от которых зависит файл. Это нужно загрузчику: он читает имена как **строки** прямо из string pool, без `SIDBase`. Так `.bin` остаётся самодостаточным.

Мы добавили ещё одну entry — `build-info`. Это **фишка компилятора**, не загрузчика. Runtime её не читает. Она нужна только sootc, чтобы ответить на вопрос «этот `.bin` ещё соответствует своему источнику и своим зависимостям?».

Layout:

```
BuildInfo               (0x20)
DepEntry[num_deps]      (0x10 * num_deps)
```

```cpp
struct BuildInfo {
    u64 source_hash;       // FNV-1a 64 от .sc
    u64 compiler_version;  // хеш версии компилятора
    u64 platform_hash;     // FNV-1a 64 от "linux"/"windows"/"darwin"
    u32 num_deps;
    u32 reserved;
};

struct DepEntry {
    sid64 name_sid;        // SID имени модуля (без .sc)
    u64   bin_hash;        // FNV-1a 64 от .bin зависимости
};
```

Ключевое решение — **`DepEntry` хранит только `sid64` имени и хеш `.bin`**. Строки имён уже есть в `requires`. Дублировать их в `build-info` не нужно: это лишние байты и лишний источник рассинхрона.

## 4. Два уровня информации о зависимостях

Зависимости описываются дважды, и это не ошибка:

- **`requires`** — строки (`const char*` в string pool). Нужны загрузчику. Работают без `SIDBase`.
- **`build-info.deps`** — `sid64` + `bin_hash`. Нужны компилятору. Работают только там, где есть `SIDBase` (а у sootc она всегда есть).

При проверке `is_fresh` направление идёт **от `requires` к `build-info`**, а не наоборот:

1. Берём `requires.m_pNames[i]` — гарантированно строка.
2. Вычисляем `SID(name)` — детерминированный CRC64.
3. Ищем в `build-info.deps` запись с этим `sid64`.
4. Берём её `bin_hash`, строим путь `.bin` из строки имени, хешируем, сравниваем.

Обратное направление (`StringIdManager(d.name_sid) → строка`) ненадёжно: `SIDBase` может не знать строку, `get_string` вернёт пустую строку, проверка молча провалится. `requires` специально сделан строками, чтобы этого не было.

## 5. Что считается «грязным»

Модуль считается грязным, если хотя бы одно из условий:

- **`source_hash` не совпал.** Изменился `.sc`.
- **`dep.bin` не совпал.** Изменился `.bin` зависимости (или его нет).
- **`.bin` отсутствует.** Нечего проверять — надо собрать.
- **`compiler_version` не совпал.** Сменилась версия компилятора.
- **`platform_hash` не совпал.** Сменилась платформа.

`compiler_version` пока — строка версии (`"sootc-v1"`). Хеш `lib.sc`/`lib.st` — следующий шаг; поле в формате уже есть, менять `.bin` не придётся.

## 6. Два режима и два уровня API

**Режимы:**

- `--force` — пересобрать всё, игнорируя `build-info`.
- `--incremental` — пересобрать только грязное.

Задаются через CLI, env (`SOOT_BUILD_MODE`), JSON (`"build-mode"`), REPL `(opt "build-mode" "incremental")`.

**Два уровня API:**

- **`save-module`** — явная команда «сохрани этот модуль». Всегда пишет `.bin` + `.h`, независимо от `is_fresh`. Пользователь попросил — надо сделать.
- **`save-module-deps`** — проектная сборка. Уважает `build_mode`: в `Incremental` пропускает свежие модули (и корень, и зависимости), пересобирает грязные.

То же для CLI: `sootc --incremental foo.sc` пропускает входной файл, если он свежий.

**Пути.** `project_root` резолвится от директории `soot.json` (если относительный) или от CWD. `out-dir` и `header-dir` — **тем же правилом**: от `json_dir`, не от `project_root`. Это важно: артефакты сборки — отдельные папки, они не обязаны лежать внутри исходников. Env и CLI резолвят от `project_root` (они не знают `json_dir`).

## 7. Примеры

**Свежий модуль, явная команда:**

```
sc> (save-module "tests/foo")
; saved D:\...\soot_gen\bin\tests\foo.bin
; OK: module 'tests/foo' saved

sc> (save-module "tests/foo")   ← второй раз
; saved D:\...\soot_gen\bin\tests\foo.bin
; OK: module 'tests/foo' saved
```

`save-module` пишет всегда — это явная команда.

**Свежий модуль, проектная сборка:**

```
sc> (save-module-deps "tests/foo")
; OK: module 'tests/foo' and dependencies saved   ← ничего не пишет, всё свежее
```

**Грязный корень, свежая зависимость:**

```
sc> (save-module-deps "tests/foo")
; saved D:\...\soot_gen\bin\tests\foo.bin         ← только foo
; OK: module 'tests/foo' and dependencies saved
```

**Удалён `bar.bin`:**

```
sc> (save-module-deps "tests/foo")
; saved D:\...\soot_gen\bin\tests\bar.bin         ← bar отсутствовал
; saved D:\...\soot_gen\bin\tests\foo.bin         ← foo грязный (dep changed)
; OK: module 'tests/foo' and dependencies saved
```

**CLI:**

```bash
sootc --incremental soot_src/tests/foo.sc
# всё свежее: "Skipping soot_src/tests/foo.sc: up to date"

sootc --force soot_src/tests/foo.sc
# всегда компилирует
```

## 8. Детерминизм

Инкрементальная сборка не должна менять результат. Тест: чистая сборка (`--force`) и инкрементальная после серии правок должны давать **побайтно одинаковый** `.bin`.

Это работает, потому что `string id` выдаются по CRC64 — порядок компиляции не важен. Автогенерируемые имена лямбд (`<base>::lambda#N`) локальны для модуля и на результат не влияют.

Если тест когда-нибудь сломается — причина будет в порядке, в скрытых входах (prelude, версия компилятора) или в `BuildInfo`. Пока тест проходит.

## 9. Build-скрипт на do-файле

В sootc есть `--do <script>`: выполнить скрипт в сессии компилятора **до** входных файлов. Это позволяет описать сборку **на самом soot**, а не на shell:

```scheme
; build.sc
(require "tests/foo.sc")
(require "tests/bar.sc")
(save-module-deps "tests/foo")
(save-module-deps "tests/bar")
```

Запуск:

```bash
sootc --incremental --do build.sc
```

Компилятор в одном процессе загрузит prelude и зависимости, выполнит `save-module-deps` для каждого модуля, и в `Incremental` пересоберёт только грязное. Это тот же инкремент, что и в `save-module-deps`, но описанный как данные, а не как флаги CLI.

Это важно для статьи: do-файл — это **способ выразить проектную сборку без внешней системы**. CMake всё ещё может запускать `sootc --do build.sc` одним правилом, но сама логика «что и в каком порядке собирать» живёт в `build.sc`.

## 10. Обсуждение: почему не файл-за-файлом и не линковка

Теоретически «правильнее» было бы компилировать каждый файл **независимо** и потом линковать. Тогда инкремент был бы тривиален: изменился файл — пересобрали один файл, линковка соберёт остальное.

Но:

1. **Это намного сложнее.** Нужен полноценный линкер, разрешение символов, ABI, порядок инициализации. В sootc этого нет — модули загружаются в runtime по имени.
2. **Ошибки линковки — самые трудные.** У них меньше всего красивых отсылок к семантике или синтаксису исходника. «Символ не найден» — это не «в строке 42 забыли скобку». Их реже видно, но когда они есть — разбираться тяжело.
3. **В sootc «линковка» — это загрузка модуля в VM.** Модули загружаются отдельно и компилируются отдельно. Это не баг, а **фича**: интерактивное программирование, REPL, динамическая среда. Ощущение «модуль загрузился — работает» — часть дизайна.

Отсюда компромисс: файл-за-файлом **можно**, и это уже работает (`sootc foo.sc` компилирует один файл). Но это **неэффективно** для проекта: каждый запуск заново грузит prelude и зависимости. Поэтому инкремент живёт **внутри** одного процесса компилятора, где prelude и зависимости уже загружены.

Брутфорс-режим (файл за файлом) реализовывать отдельно не нужно — он уже есть. Ценность в том, чтобы **один процесс** умел собирать **много файлов** с оптимизацией. Это и делает `save-module-deps` / `--do build.sc` / `--incremental`.

## 11. Что осталось

- **Хеш `lib.sc`/`lib.st` в `compiler_version`.** Сейчас — строка версии. Поле в формате есть; заменить на хеш содержимого — не менять `.bin`.
- **Очистка осиротевших `.bin`.** Модуль удалён, `.bin` остался. Нужен `--prune` или автоматическая очистка при инкрементальной сборке.
- **Depfile для CMake.** `sootc --incremental --depfile=foo.d foo.sc`, чтобы CMake знал, от чего зависит `foo.bin`. Сейчас CMake может запускать `sootc --do build.sc` одним правилом — этого достаточно, но depfile сделает интеграцию точнее.
- **Тест «чистая == инкрементальная»** — уже проходит; стоит закрепить в CI.

## 12. Выводы

Решение не идеальное. Идеальное — независимая компиляция файлов и линковка; но это намного сложнее, а ошибки линковки труднее разбирать. К тому же sootc по духу — динамическая среда, где модули загружаются и компилируются отдельно, и это часть дизайна, а не недостаток.

То, что сделано, — компромисс:

- `.bin` самодостаточен: `requires` для загрузчика, `build-info` для компилятора. Внешний манифест не нужен.
- `is_fresh` сравнивает **хеши содержимого**, не mtime. Переезд проекта, смена прав, `git checkout` — не ломают инкремент.
- Два режима (`--force` / `--incremental`) и два уровня API (`save-module` / `save-module-deps`) — явное поведение для явных команд, инкремент для проектной сборки.
- `--do build.sc` позволяет описать сборку на самом soot, без shell-скриптов.
- Детерминизм: `--force` и `--incremental` дают побайтно одинаковый `.bin`.

Это **простое** решение: нет отдельного манифеста, нет fingerprint-файлов, нет depfile (пока). Оно **работоспособное**: инкремент реально экономит время на проекте, где prelude загружается дольше, чем компилируется один модуль. И оно **соответствует стилю soot**: данные (`.bin`, `build.sc`) вместо внешних инструментов, явные команды вместо магии.

Не идеально — но работает. И это, пожалуй, лучший компромисс для компилятора, который живёт в REPL и собирает проект изнутри себя.
