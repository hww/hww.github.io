## Часть 1: Как работают имена в SOOT

В SOOT нужно различать два момента: **как компилятор находит определения и как runtime хранит их значения.**

### 1. Определения в файлах

Каждый файл `.sc` — отдельный модуль. Внутри одного файла нельзя дважды объявить одно и то же имя:

```lisp
(defun greet () "hello")
(defun greet () "hi") ; ошибка
```

Чтобы изменить функцию, нужно исправить её определение, а не добавлять второе.

При этом разные файлы могут определять одинаковые имена.

### 2. Как компилятор находит определения

Когда файл подключает другой через `(require "b.sc")`, компилятор получает доступ к его определениям.

Если несколько файлов определяют `greet`, это не ошибка: каждое определение связано со своим файлом. При разрешении имени компилятор сначала проверяет текущий файл, затем подключённые файлы.

Таким образом, **одинаковые имена в разных файлах могут существовать независимо друг от друга на уровне компиляции.**

### 3. Что происходит во время выполнения

При загрузке модуля его глобальные имена регистрируются в общей таблице `Globals`.

В этой таблице каждому имени соответствует одно текущее значение. Если несколько модулей определяют `greet`, последняя загрузка заменяет предыдущее значение.

Например, `bar.sc` определяет `greet` как `"hello"`, а `baz.sc` — как `"hi"`.

- Сначала загружен `bar`, затем `baz` — в `Globals` будет `"hi"`.
- Сначала загружен `baz`, затем `bar` — в `Globals` будет `"hello"`.

**Важно:** это правило относится к runtime. Оно не означает, что компилятор смешивает определения из разных файлов.

### 4. Что происходит в REPL

REPL — интерактивная консоль. Введённый в ней код компилятор рассматривает как отдельный виртуальный файл, например `<repl>` или `<repl-N>`.

Поэтому определение `greet` в REPL не удаляет определение из `bar.sc` в таблицах компилятора. Но после загрузки нового определения его значение может заменить прежнее в общей таблице `Globals`.

### 5. Кратко

- **Файл:** содержит собственные определения; повторное объявление имени внутри файла запрещено.
- **Компилятор:** различает определения из разных файлов и разрешает имена по правилам видимости.
- **Runtime:** хранит одно текущее значение для каждого глобального имени; последняя загрузка может его заменить.
- **REPL:** создаёт отдельные определения, которые при загрузке могут изменить значения в runtime.

## Часть 2: использование командной строки

### Компиляция одного файла

```bash
sootc --no-repl --target build soot_src/tests/bar.sc
```

Что происходит:

1\. Компилятор читает `soot_src/tests/bar.sc`.

2\. Строит для него AST (`FileNode` с именем `bar`).

3\. Генерирует `build/bar.bin` и `build/bar.h`.

4\. Выходит, потому что `--no-repl`.

**`--target build`** — папка, куда писать результаты. Если её нет, создаётся. Если не указать — по умолчанию `build`.

**Что внутри `bar.bin`:**

- `bar-greet` — скомпилированная функция.

- `top-level` — если в файле есть выражения верхнего уровня (например, `(bar-greet)` без обёртки в `defun`). Если файл содержит только объявления, `top-level` нет — модуль ничего не делает при загрузке, только регистрирует имена.

### Компиляция файла с зависимостями

```bash
sootc --no-repl --target build soot_src/tests/foo.sc
```

`foo.sc` содержит:

```lisp
(require "bar.sc")

(defun foo-greet () (bar-greet))

(foo-greet)
```

Что происходит:

1\. Компилятор читает `foo.sc`.

2\. Видит `(require "bar.sc")`.

3\. Ищет `bar.sc` — сначала рядом с `foo.sc` (`soot_src/tests/bar.sc`), потом в `PROJECT`, потом в `search_paths`.

4\. Находит, компилирует `bar.sc` как отдельный модуль, регистрирует его в runtime.

5\. Продолжает компиляцию `foo.sc`: `foo-greet` теперь видит `bar-greet`.

6\. Генерирует `build/foo.bin`, в котором записано: «этот модуль требует `bar`».

7\. Генерирует `build/bar.bin` (потому что `bar.sc` тоже скомпилировался).


### Компиляция с SIDBase


```bash
sootc --no-repl --target build --sidbase build/sidbase.bin soot_src/tests/foo.sc
```

**SIDBase** — это файл, который сопоставляет 64-битные хеши (SID) обратно строкам. Внутри `.bin` все имена хранятся как SID (`0xF9E6E6EF197C2B25`), а не как строки — это компактнее и быстрее. Но без SIDBase дизассемблер и инспектор показывают `<unknown:0x...>` вместо `bar-greet`.

**Зачем `--sidbase`:**

- Загружается в начале компиляции — чтобы все строки, встреченные в `lib.sc`, `lib.st`, и в твоих файлах, попали в SIDBase.

- Сохраняется в конце — чтобы дизассемблер мог вернуть имена.

**Если `--sidbase` не указан:**

- SIDBase не загружается (пустая).

- SIDBase не сохраняется.

- Это нормально для одноразовых компиляций, но `list-symbols`, `inspect` и `sc-run` в REPL будут показывать `<unknown:...>`.

**Рекомендация:** всегда передавай `--sidbase build/sidbase.bin`. Один файл, накапливает имена между запусками.

### Запуск REPL с runtime

```bash
sootc --runtime local --sidbase build/sidbase.bin
```

- `--runtime local` — использовать in-process VM (Carbon). Альтернативы: `--runtime null` (ничего не выполнять) или `--runtime host:port` (удалённый хост).

- `--sidbase` — загрузить SIDBase, чтобы имена резолвились.

В REPL ты можешь:

- Компилировать формы (`(defun f () ...)`).

- Загружать модули (`(load-module "./build/foo")`).

- Вызывать функции (`(sc-run foo-greet)`).

- Сохранять сессию (`(save-session "mysession")`).

- Сохранять модули (`(save-module "soot_src/tests/bar.sc")`).

## Часть 3: использование интерактивной сессии

Компилятор может быть запущен с использованием интерактивной сессии REPL.

```bash
$ sootc --repl
```

Открывшееся окно может быть использовано для инкрементальной компиляции. Для этого необходимо ввести выражение и нажать enter.

### Что происходит при вводе формы

Например, пользователь вводит в REPL:

```lisp
sci> (defun bar-greet () (print "hello"))
```

Происходит следующее:

1\. Загрузчик парсит строку в SOOT-объект.

2\. REPL-диспетчер проверяет: это REPL-команда (из `repl_commands()`) или обычная форма? `defun` — не команда, идёт дальше.

3\. Компилятор компилирует форму как отдельный модуль с именем `<repl-N>` (N растёт с каждым вводом).

4\. Runtime загружает модуль `<repl-N>`: `bar-greet` попадает в `Globals`.

5\. Runtime выполняет секцию `top-level` модуля `<repl-N>` (если есть).

6\. Форма запоминается в `m_session_forms` — истории сессии.

**Главное:** каждый REPL-ввод — **отдельный модуль** `<repl-0>`, `<repl-1>`, и т.д. Это сделано, чтобы повторное определение одного имени в разных вводах не вытесняло старое в компиляторе. В runtime `Globals` — одна, там побеждает последний.

### Проблема ошибочного ввода

Если ты введёшь неправильный `defun`, и любое другое неверное выражение компиляция упадёт, а состояние компилятора откатится к предыдущему состоянию:

```lisp
sci> (defun bar-greet (lambda () "wrong"))

; ERROR: FunctionCompiler::parse_arguments ...
```

Эта форма не попадёт в `m_session_forms` — она не часть сессии. Только успешно скомпилированные формы записываются. Поэтому `(save-session ...)` не упадёт на старых ошибках.

### Компиляция запроса зависимости

```lisp
sci> (require "bar.sc")
```

Это языковая форма, не REPL-команда. Она обрабатывается во время компиляции:

1\. Компилятор ищет `bar.sc` (рядом с текущим файлом, потом `PROJECT`, потом `search_paths`).

2\. Компилирует `bar.sc` как отдельный модуль (`FileNode("bar")`).

3\. Регистрирует модуль в runtime.

4\. Помнит, что текущий файл (или `<repl-N>`) требует `bar`.

**Результат:** `bar-greet` виден компилятору в текущей форме. Если в следующей форме ты напишешь `(bar-greet)`, компилятор найдёт его в `m_functions` (потому что `require` его туда добавил через `compile_file`).

### Загрузка модуля в среде исполнения

```lisp
sci> (load-module "./build/foo")
```

`load-module` — обычный вызов функции, которая выполняет загрузку во время работы программы. Это не команда компилятора и не команда диспетчера REPL. Она:

1\. Ищет `foo.bin` (сначала как есть, потом в `PROJECT`, потом в `search_paths`).

2\. Загружает его в `Globals`.

3\. **Рекурсивно** читает `requires: ["bar"]` и загружает `bar.bin`.

4\. **Выполняет** секцию `top-level` модуля `foo.bin` (если есть).

**Главное различие между `require` и `load-module`:**

- `require "bar.sc"` — компилирует `bar.sc`, регистрирует в runtime, добавляет в `m_functions`.

- `load-module "./build/bar"` — загружает уже скомпилированный `bar.bin` в runtime, не компилирует, не добавляет в `m_functions`.

**Что из этого следует:** после `(load-module "bar")` можно вызвать `(sc-run bar-greet)`, но нельзя написать `(bar-greet)` — компилятор не знает о `bar-greet`. Для компилятора `bar-greet` не существует, потому что `bar.bin` не проходил через `require`.

### Сохранение историю консоли

```lisp
sci> (save-session "mysession")
```

Что сохраняется:

- Все формы, которые ты ввёл в консоли и которые успешно скомпилировались.

- Не сохраняются: неудачные формы, runtime-команды (`(e)`, `(reload)`, `(gc)`), формы из `require`.

Что не сохраняется:

- Модули, загруженные через `load-module`. Они не в `m_session_forms`.

- `requires` из консоли — потому что `load-module` — это runtime, а не `require`.

Итак, `mysession.bin` сохраняет формы, введённые в консоли, а не копии всех модулей, которые консоль загружала. Если сохранённая сессия должна иметь компиляционную зависимость от исходного модуля `foo`, используй `require`. `load-module` загружает готовый бинарный модуль во время выполнения, но не создаёт такую зависимость компилятора.

**Self-dependency:** если ты сохраняешь сессию как `"bar"` и в консоли был `(require "bar.sc")`, `bar` будет удалён из `requires` — иначе `bar.bin` требовал бы сам себя, и загрузка была бы невозможна.

### Сохранение модуля

```lisp
sci> (save-module "soot_src/tests/bar.sc")
```

Что сохраняется:

- Содержимое файла `bar.sc`: его `defun`, его `require`, его `top-level`.

- Но не то, что ты вводил в консоли.

**Когда это нужно:** когда ты отредактировал `.sc` и хочешь скомпилировать именно его, не выходя из REPL. Или когда ты работаешь с несколькими файлами и хочешь пересобрать один из них.

**Self-dependency:** `save-module "bar.sc"` удаляет `bar` из `requires` — если `bar.sc` содержит `(require "bar.sc")`, это отбрасывается.

### Разница между `save-session` и `save-module`

|                    | `save-session "x"`           | `save-module "x.sc"`                  |
|--------------------|------------------------------|---------------------------------------|
| Что сохраняется    | формы, введённые в консоли   | содержимое файла `x.sc`               |
| `requires`         | из `require` в консоли       | из `require` в файле                  |
| `top-level`        | все формы консоли            | `top-level` из файла                  |
| Self-dependency    | удаляется                    | удаляется                             |
| Когда использовать | «сохранить, что я наработал» | «пересобрать файл, не выходя из REPL» |

## Часть 4: загрузка модуля

```lisp
sci> (load-module "./build/foo")

hello from bar

; => null
```

Что происходит:

1\. `load-module` ищет `foo.bin` (сначала как есть, потом `PROJECT/foo.bin`, потом `PROJECT/search_path/foo.bin`).

2\. Загружает `foo.bin` в `Globals`:

   - `foo-greet` — регистрируется.
   - `top-level` — не регистрируется (это entry point модуля, не символ).
   - `requires` — не регистрируется (это метаданные).

3\. Читает `requires: ["bar"]`.

4\. Рекурсивно загружает `bar.bin`:

   - `bar-greet` — регистрируется.

5\. Выполняет секцию `top-level` модуля `foo.bin`: `(foo-greet)` → `(bar-greet)` → `print "hello from bar"`.

6\. Печатает `hello from bar`.

**`; => null`** — `top-level` ничего не возвращает, это нормально.

## Часть 5: Вызов функции

```lisp
sci> (sc-run foo-greet)

hello from bar

; foo-greet => 1
```

`sc-run` — REPL-команда. Она:

1\. Смотрит имя `foo-greet` в `Globals`.

2\. Находит `ScriptLambda\*`.

3\. Вызывает через VM.

4\. Печатает результат (`1` — потому что `print` возвращает `1`).

**Разница между `(sc-run foo-greet)` и `(foo-greet)`:**

- `(sc-run foo-greet)` — runtime, работает, потому что `foo-greet` в `Globals`.

- `(foo-greet)` — компилятор, упадёт с `undefined function 'foo-greet'`, потому что `foo-greet` не в `m_functions` (если `foo.sc` не был `require`-нут из консоли).

**Если ты хочешь, чтобы `(foo-greet)` работал:**

```lisp

sci> (require "foo.sc")   ; ← не load-module!

```

`require` компилирует `foo.sc` и добавляет `foo-greet` в `m_functions`. После этого `(foo-greet)` компилируется и выполняется.

## Часть 6: Поиск файлов проекта

### Папки

- **`PROJECT`** — корень проекта. Определяется: `--project <dir>` → директория первого входного файла → `detect_project_root(cwd)`.

- **`build/`** — папка результатов по умолчанию (`--target build`).

- **`soot_src/`** — исходники `lib.st`, `lib.sc` (prelude).

### Файлы

- **`\*.sc`** — исходник.

- **`\*.bin`** — скомпилированный модуль.

- **`\*.h`** — C-заголовок с описанием типов (для внешних инструментов).

- **`sidbase.bin`** — SIDBase.

### Search paths

При поиске `require` и `load-module` проверяются:

1\. **Рядом с текущим файлом** (для `require`; для `load-module` — рядом с `.bin`).

2\. **`CWD`** — текущая директория.

3\. **`PROJECT`** — корень проекта.

4\. **`PROJECT / search_path`** — `., scripts, src, examples, --source-root`.

## Часть 7: типичные сценарии

### Скомпилировать один файл

```bash
sootc --no-repl --target build --sidbase build/sidbase.bin soot_src/tests/bar.sc
```

### Скомпилировать файл с зависимостями

```bash
sootc --no-repl --target build --sidbase build/sidbase.bin soot_src/tests/foo.sc
```

`bar.bin` создастся автоматически (потому что `foo.sc` требует `bar.sc`).

### Открыть REPL и загрузить модуль

```bash
sootc --runtime local --sidbase build/sidbase.bin

sci> (load-module "./build/foo")

hello from bar

sci> (sc-run foo-greet)

hello from bar
```

### Работа в REPL, сохранение сессии

```lisp
sci> (require "bar.sc")

sci> (defun my-fn () (bar-greet))

sci> (save-session "mysession")

; saved mysession.bin, requires: ["bar"]

sci> (e)
```

### Загрузка сохранённой сессии

```bash

sootc --runtime local --sidbase build/sidbase.bin

sci> (load-module "./mysession")

hello from bar

sci> (sc-run my-fn)

hello from bar

```

### Перекомпиляция файла из REPL

```lisp
sci> (save-module "soot_src/tests/bar.sc")

; saved bar.bin

sci> (load-module "./build/bar")

sci> (sc-run bar-greet)

hello from bar
```

## Часть 8: правила и подводные камни

Следующие примечания поясняют то как работает компилятор.

- **Каждое определение принадлежит файлу**
Внутри файла повторное имя — ошибка. В разных файлах — норма.

- **В глобальной области среды исполнения побеждает последний**
Не важно, сколько файлов определяют `greet`. В `Globals` — один `greet`, из последнего загруженного модуля.

- **Выражение require — компиляция, load-module — загрузка**
  - `require` → компилирует `.sc`, регистрирует в runtime, добавляет в `m_functions`.
  - `load-module` → загружает `.bin`, регистрирует в runtime, не добавляет в `m_functions`.
  Из этого следует: после `require "foo.sc"` можно писать `(foo-greet)`. После `(load-module "foo")` — только `(sc-run foo-greet)`.

- **Директива require ищет рядом с файлом**
  Если `foo.sc` в `soot_src/tests/` требует `bar.sc`, `bar.sc` найдётся в `soot_src/tests/`, даже если `soot_src/tests/` нет в `search_paths`.

- **REPL — отдельный файл**
  Всё, что вводится в консоли, принадлежит `<repl>`. Не переопределяет файлы. В runtime замещает.

- **Директива save-session отличается от save-module**
  - `save-session` — сохраняет консоль.
  - `save-module` — сохраняет файл.

- **Модуль не может зависеть на себе**
  - `save-module "bar.sc"` удаляет `bar` из `requires`. `save-session "bar"` — тоже.

Следующие примечания демонстрируют потенциальные проблемы.

- **Подводный камень: Система не проверяет рекурсивные зависимости**
  Хотя не верно их использовать в принципе, но использование зависимости a->b->a не приведет к ошибке компиляции. Это не приведет и к ошибке исполнения, но может быть утрачен детерминизм.
- **Подводный камень: `<unknown:0x...>` в `list-symbols`**
  Если запустил REPL **без** `--sidbase`, имена показываются как `<unknown:0x...>`. Это не баг, это отсутствие SIDBase. Всегда передавай `--sidbase`.
- **Подводный камень: `foo.bin` в корне проекта**
  Если ты скомпилировал `foo.sc` без `--target build`, `foo.bin` окажется в корне `PROJECT`. `load_module_recursive` ищет `foo.bin` сначала рядом с `foo.bin`, потом в `PROJECT`, потом в `search_paths`. Если старый `foo.bin` в корне — он может выиграть у нового `build/foo.bin`. Всегда используй `--target build`.

## Заключение

Чтобы ориентироваться в системе, достаточно помнить три основных различия: определения внутри исходных файлов и таблица имён runtime — не одно и то же; `require` работает с исходным кодом на этапе компиляции, а `load-module` загружает готовый бинарный модуль во время выполнения; `save-session` сохраняет историю консоли, а `save-module` — конкретный исходный файл.

- **Файл** — единица компиляции. `defun`, `deftype`, `require`.

- **Компилятор** — знает все файлы, но не смешивает.

- **Runtime** — одна `Globals`, последний побеждает.

`require` — компилирует и регистрирует. `load-module` — загружает и регистрирует. `save-session` — сохраняет консоль. `save-module` — сохраняет файл.

Всё остальное — детали.
