# Изнанка мобильного VR: инженерные правила кодинга под Oculus Quest

Разработка под автономные VR-шлемы (Oculus Quest, Pico) не прощает веры во «всеядный движок». Универсальные коробочные решения Unity, которые отлично работают на ПК, на мобильном процессоре мгновенно упираются в жесткие аппаратные тупики.

Чтобы выжать стабильные 72/90 FPS, программисту приходится перехватывать управление рендерингом и симуляцией у движка, оптимизируя код под законы мобильного железа. Ниже — практическое руководство по выстраиванию предсказуемой и детерминированной VR-архитектуры.

## 1. Баланс систем: точное определение природы Bottleneck

Качественная оптимизация — это не абстрактное уменьшение всего подряд, а поиск баланса между нагрузкой на центральный (CPU) и графический (GPU) процессоры. Главная ошибка — пытаться оптимизировать шейдеры, когда система простаивает в ожидании команд от процессора.


|![Баланс CPU/GPU](images/figure1.png)|
| :---: |
| *Figure 1 — Распределение нагрузки и эффект бутылочного горлышка (Bottleneck) между CPU и GPU.* |


- **CPU Bound:** Процессор не успевает снабжать GPU заданиями на отрисовку (Draw Calls). Заданий слишком много, но они мелкие. Количество уникальных материалов и шейдеров неоправданно велико, а размер геометрии в каждом вызове ничтожен. Ситуацию усугубляют тяжелая физика, тяжелые скрипты и пиковые всплески сборщика мусора (Garbage Collector spikes).

- **GPU Bound:** Видеокарта перегружена тяжелыми вычислениями независимо от количества Draw Calls. Это происходит из-за рендеринга огромных геометрических массивов, сложных шейдеров с множеством выборок текстур и, главное, из-за нехватки пропускной способности графической памяти. Особенно заметно это на объектах, занимающих большую часть экрана (небо, террейн) — здесь упираемся в **Texel rate limit** (скорость выборки текселей).

|![Оптимальный размер геометрии (Tris Per Batch)](images/figure2.png)|
| :---: |
| *Figure 2 — Производительность (Mv/Sec) в зависимости от размера геометрии в одном вызове (Tris Per Batch).* |


> **Правило Sweet Spot:** Мобильные платформы критически чувствительны к размеру геометрии в одном батче из-за крошечного кэша GPU. Оптимальная зона эффективности для Oculus Quest — **6–8 тысяч треугольников** на один батч. Объекты меньше этого размера создают оверхед на CPU. Объекты больше — вызывают **нелинейное падение производительности** из-за массовых кэш-промахов GPU.

## 2. Ловушка Early-Z и порядок UI: управление Z-буфером

Все знают базовое правило: непрозрачные объекты нужно рендерить **от ближних к дальним**, чтобы работал аппаратный пропуск скрытых пикселей (Early-Z). Но в Unity стандартный пайплайн содержит скрытые ловушки, ломающие этот механизм.

- **Ловушка Alpha Test (Early-Z Kill):** Если поверх идеальной непрозрачной стены рендерится полигон с alphatest (листва, решетка), в этой зоне экрана Early-Z отключается. Видеокарта не знает, прозрачен пиксель или нет, пока не выполнит фрагментный шейдер. В итоге чип тратит ресурсы на вычисление пикселей стены, которые игрок даже не увидит. Более того, в **Tile-Based Rendering (TBR) любая прозрачность (даже Test) отключает аппаратную оптимизацию для целого тайла**.

> **Решение для кода:** Измените порядок рендеринга. Если заставить непрозрачный объект рендериться **первым**, он запишется в Z-буфер. Полупрозрачный полигон выполнит обновление только реально видимых пикселей, прошедших тест глубины.

- **Переворот интерфейса (Opaque Overdraw):** По умолчанию UI в Unity рендерится **после** всей сцены (в очереди Transparent/Overlay). Если у игрока перед глазами висит большое меню, оно перерисовывает пиксели уже готового, полностью отрендеренного трехмерного мира.

> **Решение для кода:** Сместите Custom Render Queue для UI на значения `Geometry-1` или `Geometry+1`. Если интерфейс обновит Z-буфер **до** отрисовки трехмерной сцены, мобильный чип аппаратно отбросит всю тяжелую геометрию мира, которая оказалась скрыта за подложкой интерфейса.

## 3. Анатомия Tile-Based Rendering: скрытая цена прозрачности

Мобильные графические чипы используют архитектуру плиточного рендеринга (Tile-Based Rendering, TBR). Они разбивают экран на маленькие изолированные тайлы (плитки).

Когда объект имеет полупрозрачные области (alphablend или alphatest), GPU переходит в режим **Read-Modify-Write**. Чип обязан считать цвет уже отрисованного пикселя из памяти, смешать его в регистре с цветом прозрачного объекта и записать результат обратно. Наложение слоев прозрачности друг на друга порождает геометрический рост Overdraw (перерисовки), забивая узкую шину мобильной памяти.

### Программные правила борьбы с Overdraw:

1. **Жесткое выключение:** Скрипты обязаны полностью отключать (деактивировать) объекты со 100% прозрачностью. Движок не умеет отсекать их автоматически, и они продолжают крутить пустые циклы Read-Modify-Write.

2. **Tight Mesh Sprite вместо Full-Quad:** Стандартный спрайт — это квадрат из двух треугольников, где углы прозрачны. Для мобильного GPU эта пустая прозрачность стоит столько же, сколько закрашенный пиксель. Программист должен требовать от художников использования запеченных мешей по контуру объекта (Tight Mesh).

3. **UI на SpriteRenderer:** Для элементов интерфейса в VR-пространстве отдавайте предпочтение компоненту `SpriteRenderer` вместо классического тяжелого `UI Image`. На мобильных чипах он обрабатывается значительно эффективнее.

4. **Ограничение слоев и размера:** Минимизируйте количество накладывающихся прозрачных слоев и их угловой размер на экране. Каждый слой — это умножение стоимости Overdraw.

## 4. Иллюзия «коробочных систем»: зачем писать кастомный код

Универсальность стандартных подсистем Unity — главный враг производительности на Oculus Quest. Коробочные решения выполняют слишком много лишней работы. Если проект уперся в лимиты железа, единственный выход — написание легковесных кастомных менеджеров:

- **Кастомная физика (стриппинг симуляции):** Стандартный PhysX считает честные столкновения, трение и инерцию твердых тел по всем осям. Для VR-симуляции, где физика нужна лишь для детекции попаданий и простых анимаций, это недопустимый оверхед. Кастомная, математически урезанная физическая система (например, чистый обсчет пересечений сфер и лучей) высвобождает значительную долю ресурсов CPU.

- **Кастомный Occlusion Culling (OCS):** Родной OCS в Unity запекает огромные объемы данных видимости, требуя много оперативной памяти, и крайне неэффективен, если сцена генерируется в рантайме. Кастомная система, написанная под конкретную топологию игры (например, жесткое переключение видимости комнат при прохождении дверей), работает детерминированно и не тратит память.

> **Когда OCS эффективна:** Сцена с комнатами, коридорами, каньонами. Движущаяся камера.
> **Когда OCS бесполезна:** Все объекты видны всегда. Большие монолитные объекты (здания, горы). Мало памяти. Динамически генерируемая сцена.

- **Разбиение больших объектов и самопересечений:** Движок не умеет эффективно сортировать и отсекать гигантские меши (здания, ландшафт) или самопересекающуюся геометрию. Задача программиста — на этапе импорта или рантайм-сборки разделять такие объекты на независимые модули. Это позволяет движку корректно определять их реальный логический центр (Origin), правильно сортировать по глубине и эффективно использовать Early-Z и Occlusion Culling.

## 5. Борьба за потоки: разрыв однопоточного наследия

Мобильные процессоры ARM обладают слабой производительностью на одно ядро. Стандартный монолитный код на C#, размазанный по сотням методов `Update()`, загружает лишь один главный поток Unity. Одно ядро шлема закипает от перегрузки, вызывая падение кадров, пока остальные три ядра простаивают.

Единственный способ выжить в мобильном VR — перейти на Data-Oriented подход на уровне выполнения логики:

- **Burst Compiler & Job System:** Вся тяжелая математика — расчет траекторий частиц, симуляция кастомной физики, логика поведения ИИ, обсчет стейт-машин — должна быть вынесена из `MonoBehaviour` в чистые структуры `IJobParallelFor`.

- **В чем физика процесса:** Job System автоматически разбивает массивы данных на порции и равномерно загружает все ядра процессора. Burst Compiler при этом трансформирует C#-код в оптимизированный машинный код под архитектуру ARM, выжимая максимум из регистров процессора.

## 6. Директивное управление (Hard-coded solutions)

Когда автоматические системы оптимизации и динамический стриминг не могут гарантировать стабильный FPS в 100% игровых ситуаций, инженер обязан переходить на **ручное, жесткое управление рантаймом**.

Вместо того чтобы заставлять движок каждую секунду вычислять расстояния и динамически подстраивать параметры, внедряйте в код директивные скрипты-режиссеры, привязанные к конкретным триггерам сцены:

```csharp
// Пример жесткого рантайм-управления параметрами сцены
void OnPlayerEnterHeavyZone() {
    ParticleSystem.timeMax = 0.5f;      // Урезаем время жизни частиц
    ShadowQuality.disableDistance = 10f; // Выключаем дальние тени
    RenderScale.value = 1.0f;           // Сбрасываем render scale
    DeactivateHiddenObjects();          // Принудительно выгружаем невидимое
}
```

По мере прохождения уровня скрипт должен принудительно управлять памятью, используя систему **Addressables** для жесткой выгрузки неиспользуемых текстур и префабов, не дожидаясь, пока ленивый Garbage Collector вызовет пиковое падение производительности.

## Итоговый чек-лист для программиста VR

| Действие | Приоритет |
|----------|-----------|
| Определить **Bottleneck** (CPU Bound vs GPU Bound) через профилировщик | 🔴 Высший |
| Минимизировать количество **шейдеров** (один opaque, один alpha, один unlit) | 🔴 Высший |
| Минимизировать количество **материалов** | 🔴 Высший |
| Использовать **Sweet Spot** (6–8K треугольников на батч) | 🔴 Высший |
| Изменить **порядок рендеринга UI** (Custom Render Queue = Geometry-1) | 🔴 Высший |
| Использовать **Job System + Burst Compiler** для тяжелой логики | 🔴 Высший |
| Деактивировать объекты со **100% прозрачностью** | 🟡 Средний |
| Использовать **Tight Mesh** для спрайтов вместо Full-Quad | 🟡 Средний |
| Разбивать **Large Game Objects** на модули | 🟡 Средний |
| Избегать **Alpha Test/Blend** в TBR, особенно на больших объектах | 🟡 Средний |
| Использовать **Hard-coded управление** для критических участков | 🟡 Средний |
| Оптимизировать сетку только если в ней **> 500 треугольников** | 🟢 Низкий |
| Использовать Addressables для управления памятью | 🟢 Низкий |
